Chapter I

The Problem With Model Weights

A seven-billion-parameter language model is, at its core, a collection of named tensors. Thousands of them. Each one a dense block of floating-point numbers—attention projections, feed-forward gates, embedding tables, layer norms—keyed by names like model.layers.31.self_attn.q_proj.weight. The question that every inference runtime, every training pipeline, and every model distribution system must answer is deceptively simple: how do you store and retrieve these tensors efficiently, safely, and from any programming language?

The incumbent answers are unsatisfying. SafeTensors is single-language in spirit, bolted onto Python's ecosystem. GGUF is a monolith designed around llama.cpp's specific needs. HDF5 is a 30-year-old format that requires a C library the size of a small operating system. None of them were designed for the reality of modern ML infrastructure: models served from Go runtimes, preprocessed in Python, validated in Rust, loaded in C for CUDA kernels, and orchestrated from TypeScript control planes. You need one format that works natively in all five, with checksums you can trust, compression you can control, and alignment that lets you mmap directly into GPU memory.

Shard is that format. A 64-byte header, 48-byte index entries, xxHash64 name lookups, CRC32C integrity checks, zstd/LZ4 compression, and 64-byte alignment by default. Five language implementations—all binary-compatible, all producing identical bytes for identical inputs. No runtime dependencies beyond a compression library. No schema negotiation. No version hell. You write a shard in Python, read it in C, stream it in Go, validate it in Rust. The bytes are the contract.

Chapter II

The Wire Format

Shard v2 is a binary container format designed for one purpose: packing named blobs—typically ML model weights, tensors, and metadata—into a single seekable file with O(1) lookup by name. The format uses a fixed 64-byte header, a flat index of 48-byte entries, a string table, and an aligned data section. Everything is little-endian. There is no tree structure, no nested containers, no variable-length headers. It is deliberately simple.

The magic bytes are SHRD (0x53, 0x48, 0x52, 0x44). Version is always 0x02—there is no v1 in this codebase; the numbering implies a predecessor that was either discarded or never formalized.

Compression

Entries can be individually compressed with zstd or LZ4. The writer applies compression only when the entry is at least 256 bytes and compression achieves at least a 90% ratio (compressed size ≤ 90% of original). Otherwise, the entry is stored raw. This prevents small entries from being inflated by compression framing overhead.

The compression decision happens per-entry, not per-file. Each entry's index flags record whether it is compressed and which algorithm was used. This means a single shard can contain a mix of compressed and uncompressed entries—small metadata entries stored raw alongside multi-megabyte weight tensors compressed with zstd.

ParameterValueRationale
MIN_COMPRESS_SIZE 256 bytes Below this threshold, zstd/LZ4 framing overhead dominates
Savings threshold 90% (9/10) Compressed size must be ≤ 90% of original; otherwise stored raw
MAX_DECOMPRESS_SIZE 1 GB Anti-decompression-bomb safety cap
Compression Decision Logic (from Go reference) 
// MIN_COMPRESS_SIZE = 256 bytes
// Compression must save at least 10% (ratio <= 0.90)
if len(data) < MinCompressSize {
    return data, false  // too small
}
compressed := zstdEncode(data)
if len(compressed) >= len(data) * 9 / 10 {
    return data, false  // savings too small
}
return compressed, true

The Shard Analogy

The package documentation in shard.go offers a crisp analogy for the format's place in the stack:

From shard.go

"Think of it as a ZIP file optimized for tensors—but with mmap support, 64-byte alignment for SIMD, and streaming writes."

Cowrie and GLYPH are value codecs (individual "files"). Shard is a container format (a "directory" holding many files). A shard typically contains Cowrie-encoded or TensorV1-encoded entries, but the format is agnostic—entries can be any binary data.

Streaming Writes

The Go implementation provides two writer types: ShardV2Writer for standard buffered writes, and ShardV2StreamWriter for zero-copy streaming. The stream writer is designed for very large models where you cannot hold all entries in memory. It requires pre-declaring the entry count, writes the header and index with placeholder offsets, streams data entries sequentially, then seeks back to finalize the header and index.

Streaming write pattern (from shard.go docs) 
// Streaming write (for very large models):
sw, _ := NewShardV2StreamWriter("model.shard", ShardRoleMoSH, 1000)
sw.BeginData()
sw.WriteEntry("layer.0.weight", tensorBytes)
sw.Finalize()

Key Divergences

Divergence: TypeScript

The TypeScript implementation takes a Buffer in the constructor rather than a file path. It operates entirely in-memory. This makes sense for its primary use case (Node.js/browser), but means it cannot mmap large files the way Go, Rust, and C do.

Divergence: C NULL Handling

The C implementation rejects NULL data for zero-length entries. All other languages accept a zero-length buffer. This was documented in the cross-language parity commit (ae38c57) but intentionally left as a C-specific guard: passing NULL to memcpy is undefined behavior in C even when the length is zero.

Lookup Strategy

All implementations use xxHash64 for name hashing. Lookup computes the hash, then walks the index linearly to find a matching hash, confirming by comparing the actual name from the string table. This is O(n) in the worst case but typically O(1) for unique names—xxHash64 collisions are vanishingly rare in practice. Go and Rust build an in-memory hash map on open for O(1) amortized lookup.

Chapter V

Security Architecture

A binary container format that reads untrusted files is an attack surface. The shard codec addresses this with four interlocking defenses: hard limits on structure sizes, cryptographic checksums on every entry, integer overflow protection at the boundary between wire format and memory, and a comprehensive corpus of corrupt test fixtures.

Safety Limits

Every reader enforces these constants before allocating memory or reading data. They are identical across all five implementations.

LimitValuePurpose
MAX_ENTRY_COUNT 10,000,000 Prevents allocation of unbounded index arrays
MAX_INDEX_SIZE 1 GB Caps total index section memory
MAX_STRING_TABLE_SIZE 100 MB Prevents string table from consuming all memory
MAX_DECOMPRESS_SIZE 1 GB Caps decompressed entry size (anti-bomb)
MIN_COMPRESS_SIZE 256 B Entries below this are never compressed

Checksums and Hashing

The format uses two hash functions for different purposes.

CRC32C Castagnoli — Data Integrity

Every entry carries a CRC32C checksum of its uncompressed data, computed at write time and verified on read (when the FLAG_HAS_CHECKSUMS header flag is set, which is the default). CRC32C was chosen over CRC32 for its hardware acceleration on modern x86 (SSE 4.2) and ARM (CRC extension) processors.

xxHash64 — Name Lookup

Each entry stores the xxHash64 of its name for fast lookup. The reader computes the hash of the requested name and scans the index for a match, then confirms by comparing the actual name from the string table. This two-step process avoids false positives from hash collisions while keeping the common path fast.

Integer Overflow Protection

The Go reference implementation introduced a dedicated module, intconv.go, for safe conversion between unsigned wire-format integers and signed platform integers. This is more subtle than it appears: Go's int is platform-sized (32-bit on 32-bit systems), so a uint64 value from the wire can silently truncate.

intconv.go — Safe uint64-to-int conversion 
const maxShardInt64 = 1<<63 - 1

func uint64ToInt(v uint64) (int, bool) {
    if strconv.IntSize == 32 {
        if v > 1<<31-1 {
            return 0, false
        }
    } else if v > maxShardInt64 {
        return 0, false
    }
    // #nosec G115 -- bounds checked above
    return int(v), true
}

func uint64ToInt64(v uint64) (int64, bool) {
    if v > maxShardInt64 {
        return 0, false
    }
    return int64(v), true
}
The C malloc overflow

Commit 2544d22 fixed a critical C bug: the index allocation computed entry_count * INDEX_ENTRY_SIZE without checking for multiplication overflow. A crafted shard with entry_count = 0xFFFFFFFF could wrap the multiplication to a small value, allocating a tiny buffer and then writing far beyond it. The fix validates entry_count against MAX_ENTRY_COUNT before the multiplication.

Compression Safety

Decompression is bounded by MAX_DECOMPRESS_SIZE (1 GB). The Go reference implementation additionally validates that zstd decompression produces exactly origSize bytes—not fewer, not more. This prevents both truncated decompression (silent data loss) and decompression bombs (malicious origSize that allows unbounded output).

Validation Chain

On open, every reader performs the same sequence of validations. Failing any check aborts the open and returns an error. This chain is worth enumerating because it represents the threat model:

Reader Validation Chain (all 5 languages)
1. Read 64 bytes — reject if file is too short
2. Verify magic = "SHRD" — reject if wrong
3. Verify version = 0x02 — reject if unsupported
4. Verify index_entry_size = 48 — reject if unexpected
5. Verify entry_count ≤ MAX_ENTRY_COUNT (10M) — reject if too many
6. Compute index_size = entry_count × 48 — check for overflow
7. Verify index_size ≤ MAX_INDEX_SIZE (1 GB) — reject if too large
8. Read index entries — reject if file truncated
9. Read string table — verify size ≤ MAX_STRING_TABLE_SIZE (100 MB)
10. Validate total_file_size against actual file size — reject on mismatch
11. Validate each entry's data_offset + disk_size within file bounds
12. Validate name_offset + name_len within string table bounds

The C Use-After-Free (PR #1)

The very first pull request to the shard repository fixed a use-after-free in the C test suite. In test_metadata.c, the test buffer was being freed before shard_v2_close() was called on the reader. Since the reader held a pointer into the buffer (for mmap-style access), closing it after the free triggered undefined behavior. The fix was simple: reorder the free() to come after shard_v2_close(). But the bug illustrates why the C implementation is the most dangerous to work with—memory lifetime is the caller's responsibility.

Defense in Depth

The security model assumes adversarial input. Every offset from the wire is validated against the file size. Every count is checked against a hard maximum before allocation. Every checksum is verified before the data is returned to the caller. The format trusts nothing it reads.

Chapter VI

The Robustness Layer

The final commit of the sprint introduced something unusual: a data-driven test framework that treats correctness as a truth table. Rather than writing ad hoc tests in each language, the robustness layer defines 9 behavioral assertions that every implementation must satisfy. The same 9 cases are tested in Go, Python, TypeScript, Rust, and C. If any language diverges, the truth table catches it.

The Truth Table

Each case is a proposition about the format's behavior. The test either constructs the condition programmatically or loads a corrupt fixture.

#CaseExpected BehaviorMethod
1 Duplicate entry names Rejected at write or read time Programmatic: write two entries with the same name
2 Zero-length entry Valid: write and read back empty data Programmatic: write entry with []byte{}
3 Unicode entry name Valid: name preserved through roundtrip Programmatic: write entry named "日本語"
4 Bad magic bytes Rejected on open Fixture: corrupt_bad_magic.shard
5 Truncated header Rejected on open Fixture: corrupt_truncated_header.shard
6 CRC mismatch Rejected on open or on verified read Fixture: corrupt_crc_mismatch.shard
7 Truncated data section Rejected on open or on read Fixture: corrupt_truncated_data.shard
8 Entry count overflow Rejected on open Fixture: corrupt_entry_count_overflow.shard
9 Empty input (0 bytes) Rejected on open Programmatic: write empty file, attempt to open
Design Choice

Cases 4–8 accept two valid behaviors: rejection on open or rejection on read. This flexibility accommodates structural differences between implementations. Go and Rust validate eagerly (fail-fast on open). C and Python may defer validation until the affected entry is actually accessed. Both strategies are correct as long as the invalid data never reaches the caller.

Performance Cliff Detection

The Go implementation includes performance cliff tests that guard against accidentally quadratic behavior. The test writes shards with increasing entry counts (100, 1,000, 5,000) and measures write+read time. If any step takes more than 20× the previous step, the test fails—signaling potential O(n²) behavior in what should be an O(n) operation.

Perf cliff test — quadratic blowup detection 
func TestPerfCliff_ManyEntries(t *testing.T) {
    sizes := []int{100, 1000, 5000}
    var lastDuration time.Duration

    for _, size := range sizes {
        // ... write 'size' entries, read them all back ...
        dur := time.Since(start)

        if lastDuration > 0 && dur > lastDuration*20 {
            t.Errorf(
                "possible quadratic blowup at size=%d: took %v, previous %v",
                size, dur, lastDuration,
            )
        }
        lastDuration = dur
    }
}

A second test checks large entry sizes (1 KB, 1 MB, 10 MB) and fails if any single entry takes more than 10 seconds to write and read back. This catches compression pathologies or accidental full-file copies.
